# Задание 2. Мониторинг
## Мотивация
* рост клиентской лояльности за счет более высокой доступности системы и меньшего числа ошибок, т.к. проблемы идентифицируются и устраняются либо превентивно, либо быстрее - клиенты их замечают реже 
* оптимизация расходов на железо: мониторинг позволит более точно перераспределять железо от ненагруженных сервисов к сервисам с высокой утилизацией и докупать новые мощности при реальной необходимости для системы в целом
* выгоднее один раз потратить ресурсы на настройку качественного мониторинга, чем технической команде постоянно заниматься ручным разбором ошибок по логам в поисках причин обращений клиентов или тушения пожаров после масштабирования бизнеса бех масштабирования инфораструктуры
* мониторинг позволит заранее прогнозировать возможности масштабирования системы в соответствии с бизнес-планами и планировать обоснованные закупки новых ресурсов без форсмажоров и по оптимальной цене
* дополнительные данные мониторинга могут привести к бизнес-инсайтам и более взвешенному обоснованию стратегических решений, т.к. содержат расширенную информацию о повседневном поведении пользователей, о корреляции поведения с маркетинговыми акциями и т.д.
## Выбор подхода к мониторингу
* для серверов Shop DB, MES DB, S3 Storage "3d files" и RabbitMQ "Message Queue" выбираем метод USE, т.к. речь про инфраструктурные ресурсы, производительность которых снижается при интенсивном использовании
* для бэкенд приложений Shop API, CRM API, MES API и для веб-приложений Shop, MES и CRM выбираем LTES aka «Четыре золотых сигнала», т.к. помимо показателей RED хочется смотреть "насыщенность" очередей веб серверов по отношению к их максимальному размеру
### Набор метрик для отслеживания
#### Shop
* Shop API
  * Number of requests (RPS) for internet shop API
    >  Зачем: показатель RPS позволяет оценить обычную и пиковую нагрузки для обеспечения стабильной работы и своевременного масштабирования в корреляции с системными показателями
    >>  Метки: регион; имя сервиса; URL эндпойнта;
  * Number of requests (RPS) per user for internet shop API
    >  Зачем: показатель RPS по пользователю позволяют оперативно выявить аномальное/несанкционированное/нецелевое использование API
    >>  Метки: пользователь; URL эндпойнта;
  * CPU % for shop API
    >  Зачем: системный показатель утилизации выделенного ресурса CPU, при превышении порога в 80% сигнализирующей о возможной деградации производительности и необходимости масштабирования
    >>  Метки: регион, имя сервис
  * Memory Utilisation for shop API
    >  Зачем: системный показатель утилизации выделенного ресурса Memory, при превышении порога в 90% сигнализирующей о возможном отказе сервиса и необходимости масштабирования
    >>  Метки: регион, имя сервис
  * Response time (latency) for shop API
    >  Зачем: показатель для SLA и удовлетворения пользователей, рост которого сигнализирует о необходимости оптимизации логики сервиса или масштабирования
    >>  Метки: регион; имя сервиса; URL эндпойнта;
  * Number of HTTP 200 for shop API
    >  Зачем: показатель успешных ответов, просадка которого сигнализирует о проблемах в работе сервиса. При это просадка здесь может быть не отражена ростом ошибочных кодов
    >>  Метки: регион; имя сервиса; URL эндпойнта;
  * Number of HTTP 500 for shop API
    >  Зачем: показатель неуспешных ответов, рост которого сигнализирует о проблемах в работе сервиса - ошибки в логике или нехватка ресурсов
    >>  Метки: регион; имя сервиса; URL эндпойнта;
  * Number of simultanious sessions for shop API
    >  Зачем: показатель количества одновременно активных сессий позволяет оценить обычную и пиковую нагрузки для обеспечения стабильной работы и своевременного масштабирования в корреляции с системными показателями. Резкое увеличение может сигнализировать о DDOS атаке
    >>  Метки: регион; имя сервиса
  * Kb tranferred (received) for shop API
    >  Зачем: системный показатель объемов получаемых данных позволяет оценить текущую нагрузку на сеть и планировать своевременное масштабирование. Если показатель значительно превышает доступную полосу пропускания, возможны ухудшение качества взаимодействия пользователей с сервисом. Резкое увеличение может сигнализировать о проблемах безопасности, например, несанкционированном доступе или попытке взлома/DDOS атаки
    >>  Метки: регион; имя сервиса
  * Kb provided (sent) for shop API
    >  Зачем: системный показатель объемов передаваемых данных позволяет оценить текущую нагрузку на сеть и планировать своевременное масштабирование. Рост показателя может сигнализировать о необходимости внедрения кеширования и компрессии на фронтах. Если объем передачи значительно превышает доступную полосу пропускания, возможны задержки загрузки страниц и ухудшение качества взаимодействия пользователей с сервисом. Резкое увеличение может сигнализировать о проблемах безопасности, например, несанкционированном доступе или попытке взлома системы.
    >>  Метки: регион; имя сервиса
* Shop DB
  * Memory Utilisation for shop db instance
    >  Зачем: системный показатель утилизации выделенного ресурса Memory, при превышении порога в 90% сигнализирующей о возможной деградации из-за использования свопа и дальнейшего отказа БД
    >>  Метки: регион; имя инстанса
  * Number of connections for shop db instance
    >  Зачем: системный показатель количества подключений к БД позволяет оценить обычную и пиковую нагрузки для обеспечения стабильной работы БД и своевременного масштабирования в корреляции с системными показателями. При превышении максимально допустимого значения начнутся отказы в обслуживании
    >>  Метки: регион; имя инстанса
  * Size of shop db instance
    >  Зачем: системный показатель утилизации выделенного ресурса Disk, при превышении порога в 90% сигнализирующей о возможной деградации из-за роста фрагментации и дальнейшего отказа БД
    >>  Метки: регион; имя инстанса

#### RabbitMQ
  * MessageQueue
    * Number of dead-letter-exchange letters in RabbitMQ  
      >  Зачем: число сообщений, отброшенных из основной очереди. Рост показателя может сигнализировать на ошибки в работе консьюмерами MES/CRM или превышение длины очереди из-за слишком высокой скорости публикации продьюсерами

      >  Зачем: Число сообщений в очереди, обрабатываемых в моменте. Рост показателя (особенно постоянный), сигнализирует на недостаточную производительность потребителей или слишком высокую скорость публикации продьюсерами
      >>  Метки: имя очереди; продюсер
