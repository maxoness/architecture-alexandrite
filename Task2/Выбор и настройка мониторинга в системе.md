# Задание 2. Мониторинг
## Мотивация
* рост клиентской лояльности за счет более высокой доступности системы и меньшего числа ошибок, т.к. проблемы идентифицируются и устраняются либо превентивно, либо быстрее - клиенты их замечают реже 
* оптимизация расходов на железо: мониторинг позволит более точно перераспределять железо от ненагруженных сервисов к сервисам с высокой утилизацией и докупать новые мощности при реальной необходимости для системы в целом
* выгоднее один раз потратить ресурсы на настройку качественного мониторинга, чем технической команде постоянно заниматься ручным разбором ошибок по логам в поисках причин обращений клиентов или тушения пожаров после масштабирования бизнеса бех масштабирования инфораструктуры
* мониторинг позволит заранее прогнозировать возможности масштабирования системы в соответствии с бизнес-планами и планировать обоснованные закупки новых ресурсов без форсмажоров и по оптимальной цене
* дополнительные данные мониторинга могут привести к бизнес-инсайтам и более взвешенному обоснованию стратегических решений, т.к. содержат расширенную информацию о повседневном поведении пользователей, о корреляции поведения с маркетинговыми акциями и т.д.
## Выбор подхода к мониторингу
* для серверов Shop DB, MES DB, S3 Storage "3d files" и RabbitMQ "Message Queue" выбираем метод USE, т.к. речь про инфраструктурные ресурсы, производительность которых снижается при интенсивном использовании
* для бэкенд приложений Shop API, CRM API, MES API и для веб-приложений Shop, MES и CRM выбираем LTES aka «Четыре золотых сигнала», т.к. помимо показателей RED хочется смотреть "насыщенность" очередей веб серверов по отношению к их максимально допустимому размеру
### Набор метрик для отслеживания
#### Shop
* Shop API
  * Number of requests (RPS) for internet shop API
    >  Зачем: показатель RPS позволяет оценить обычную и пиковую нагрузки для обеспечения стабильной работы и своевременного масштабирования в корреляции с системными показателями
    >>  Метки: регион; имя сервиса; URL эндпойнта; HTTP-метод; статус авторизации
  * Number of requests (RPS) per user for internet shop API
    >  Зачем: показатель RPS по пользователю позволяют оперативно выявить аномальное/несанкционированное/нецелевое использование API
    >>  Метки: регион; пользователь; URL эндпойнта; HTTP-метод; статус авторизации
  * Number of queued requests for internet shop API
    >  Зачем: показатель количества запросов в очереди на обработку worker-ами вэбсервера позволяет оценить общую производительность сервиса. Его рост сигнализирует о повышенной активности пользователей, некорректно настроенном числе worker-ов или проблемах производительности, что в дальнейшем может привести к отказам в обслуживании и негативно сказаться на клиентском опыте 
    >>  Метки: регион; имя сервиса;
  * CPU % for shop API
    >  Зачем: системный показатель утилизации выделенного ресурса CPU, при превышении порога в 80% сигнализирующей о возможной деградации производительности и необходимости масштабирования
    >>  Метки: регион; имя сервиса
  * Memory Utilisation for shop API
    >  Зачем: системный показатель утилизации выделенного ресурса Memory, при превышении порога в 80% сигнализирующей о возможном отказе сервиса и необходимости масштабирования
    >>  Метки: регион; имя сервиса
  * Response time (latency) for shop API
    >  Зачем: показатель задержки в ответах приложения, краеугольный для SLA и удовлетворения пользователей, рост которого сигнализирует о необходимости оптимизации логики сервиса или масштабирования
    >>  Метки: регион; имя сервиса; URL эндпойнта; HTTP-метод
  * Number of HTTP 200 for shop API
    >  Зачем: показатель успешных ответов, просадка которого сигнализирует о проблемах в работе сервиса. При это просадка здесь может быть не отражена ростом ошибочных кодов
    >>  Метки: регион; имя сервиса; URL эндпойнта; HTTP-метод
  * Number of HTTP 500 for shop API
    >  Зачем: показатель неуспешных ответов, рост которого сигнализирует о проблемах в работе сервиса - ошибки в логике или нехватка ресурсов
    >>  Метки: регион; имя сервиса; URL эндпойнта; HTTP-метод
  * Number of simultanious sessions for shop API
    >  Зачем: показатель количества одновременно активных сессий позволяет оценить обычную и пиковую нагрузки для обеспечения стабильной работы и своевременного масштабирования в корреляции с системными показателями. Резкое увеличение может сигнализировать о DDOS атаке
    >>  Метки: регион; имя сервиса; ip-адрес
  * Kb tranferred (received) for shop API
    >  Зачем: системный показатель объемов получаемых данных позволяет оценить текущую нагрузку на сеть и планировать своевременное масштабирование. Если показатель значительно превышает доступную полосу пропускания, возможны ухудшение качества взаимодействия пользователей с сервисом. Резкое увеличение может сигнализировать о проблемах безопасности, например, несанкционированном доступе или попытке взлома/DDOS атаки
    >>  Метки: регион; имя сервиса; HTTP-метод
  * Kb provided (sent) for shop API
    >  Зачем: системный показатель объемов передаваемых данных позволяет оценить текущую нагрузку на сеть и планировать своевременное масштабирование. Рост показателя может сигнализировать о необходимости внедрения кеширования и компрессии на фронтах. Если объем передачи значительно превышает доступную полосу пропускания, возможны задержки загрузки страниц и ухудшение качества взаимодействия пользователей с сервисом. Резкое увеличение может сигнализировать о проблемах безопасности, например, несанкционированном доступе или попытке взлома системы.
    >>  Метки: регион; имя сервиса; HTTP-метод
* Shop DB
  * Memory Utilisation for shop db instance
    >  Зачем: системный показатель утилизации выделенного ресурса Memory, при превышении порога в 80% сигнализирующей о возможной деградации из-за использования свопа и о дальнейшем отказе БД
    >>  Метки: регион; имя инстанса

При превышении максимально допустимого значения для пула соединений начнутся отказы в обслуживании
    >>  Метки: регион; имя инстанса

    >  Зачем: системный показатель утилизации выделенного ресурса Disk, при превышении порога в 95% сигнализирующей о возможной деградации из-за роста фрагментации и о дальнейшем отказе БД, т.е. требуется экстренное масштабирование
    >>  Метки: регион; имя инстанса

#### RabbitMQ
  * MessageQueue
    * Number of dead-letter-exchange letters in RabbitMQ  
      >  Зачем: число сообщений, отброшенных из основной очереди. Рост показателя может сигнализировать на ошибки в работе консьюмеров MES/CRM или превышение длины очереди из-за слишком высокой скорости публикации продюсерами
      >>  Метки: имя очереди; продюсер
    * Number of message in flight in RabbitMQ
      >  Зачем: Число сообщений в очереди, обрабатываемых в моменте. Рост показателя (особенно постоянный), сигнализирует на недостаточную производительность потребителей или слишком высокую скорость публикации продюсерами
      >>  Метки: имя очереди; продюсер
    * Number of consumers
      >> Зачем: число активных консьюмеров очереди. Может сигнализировать о сетевых проблемах/проблемах конфигурации (не типично низкое число) или о некорректной/неэффективной логике работы консьюмеров (не типично высокое число)
      >> Метки: имя очереди; имя ноды
    * CPU % for RabbitMQ
      > Зачем: системный показатель утилизации выделенного ресурса CPU, при превышении порога в 80% сигнализирующей о возможной деградации производительности и необходимости масштабирования
      >> Метки: имя ноды
    * Memory Utilisation for RabbitMQ
      >  Зачем: системный показатель утилизации выделенного ресурса Memory, при превышении порога в 90% сигнализирующей о возможном отказе сервиса и необходимости масштабирования
      >>  Метки: имя ноды
    * Disk Utilisation for RabbitMQ
      >  Зачем: системный показатель утилизации выделенного ресурса Disk, при превышении порога в 95% сигнализирующей о возможной деградации из-за роста фрагментации и о дальнейшем отказе БД, т.е. требуется экстренное масштабирование
      >>  Метки: имя ноды
    * Message publish rate
      >  Зачем: Дополнительные показатель скорости публикации сообщений продюсерами позволяет оценить возможности масштабирования, а также идентифицировать проблемы производительности с конкретными очередями (когда публикация интенсивнее доставки) или продюсерами (eg. какой-то залип и инициировал лавину публикаций)
      >>  Метки: имя очереди; имя ноды; продюсер
    * Message delivery rate
      >  Зачем: Дополнительные показатель скорости доставки сообщений консьюмерам позволяет оценить возможности масштабирования, а также идентифицировать проблемы производительности с конкретными очередями или нодами
      >>  Метки: имя очереди; имя ноды; консьюмер

## План действий
* Развертывание инфраструктуры для сбора и хранения метрик
  * Создать инстанс time-series базы данных с использованием Prometheus для сбора метрик.
  * Настроить долговременное хранение метрик в Prometheus, подключив решения Thanos или Cortex.
  * Настроить сбор логов и метрик для пересылки метрик из RabbitMQ, API и баз данных в time-series хранилище Prometheus.
* Интеграция с сервисами и сбор метрик
  * Добавить экспорт метрик в Shop API, CRM API и MES API.
  * Настроить экспорт метрик из RabbitMQ.
  * Настроить экспорт метрик из баз данных (Shop DB, MES DB).
* Настройка мониторинга инфраструктуры
  * Интегрировать мониторинг ресурсов Yandex Cloud для мониторинга EC2 инстансов (CPU, память, дисковое пространство) и S3-хранилища.
  * Подключить метрики балансировщиков нагрузки и сети для мониторинга сетевых запросов, времени ответа и загрузки каналов.
* Визуализация данных
  * Развернуть систему визуализации метрик Grafana. Настроить дашборды для отображения ключевых метрик для каждой части системы (Shop, CRM, MES, RabbitMQ).
  * Создать дашборды по API для мониторинга RPS, ошибок, задержек, использования ресурсов и т.д.
  * Создать дашборды по RabbitMQ для мониторинга очередей и использования ресурсов.
  * Настроить дашборды по базам данных для анализа использования ресурсов и соединений.
* Настройка алертов
  * Настроить правила оповещения (алерты) в системе мониторинга для ключевых метрик: ошибки 500, высокие задержки, превышение пределов использования системных ресурсов, переполнение очередей и т.д.
  * Добавить алерты для RabbitMQ на количество dead-letter сообщений, долгую обработку сообщений в очереди (можно судить по Number of message in flight) и количество активных консьюмеров (аномальные границы).
  * Настроить алерты для баз данных: превышение лимитов соединений, медленные запросы/блокировки, превышение WARN порогов объема данных.
  * Настроить алерты для API на задержки ответов, ошибки и аномальные просадки.
* Оптимизация системы на основе метрик
  * Проанализировать собранные данные для выявления узких мест.
  * Разработать план по масштабированию компонентов системы на основе анализа данных.
* Документация и обучение
  * Создать документ по метрикам и алертам: описать, какие метрики собираются и зачем, какие действия нужно выполнять при срабатывании алертов.
  * Провести обучение команды по работе с мониторингом: как использовать дашборды, анализировать данные и реагировать на алерты.
* Тестирование системы мониторинга
  * Провести нагрузочное тестирование систем мониторинга для проверки работоспособности под реальной или кратно увеличенной нагрузкой для валидации выбранных пороговых значений.
  * Провести тестирование всех алёрты: убедиться, что оповещения срабатывают при достижение пороговых значений.
## Показатели насыщенности
* __Утилизация CPU/MEM__ для Shop API, CRM API, MES API и для веб-приложений Shop, MES и CRM
  * Пороговое значение: общепринятые 80%, если ресуры выделялись без значительного запаса
  * Обоснование: если показатель утилизации CPU/MEM выше 80%, сервис может начать обрабатывать запросы медленнее, что негативно скажется на производительности сервисов и качестве обслуживания, а в дальнейшем может привести к полному отказу приложения
  * Действия при превышении:
    * Сгенерировать алёрт и отправить его по выбранным каналам коммуникации с дежурным инженером (письмо, смс, мессенджер) 
    * Завести тикет в трекере задач (например, Jira), чтобы в рабочее время провести анализ производительности.
    * Если утилизация не спадает в течение 10 минут, произвести автоскейлинг, добавив новый инстанс приложения для распределения нагрузки 
    * Если превышение продолжается более 20 минут, совершить звонок дежурному инженеру и отправить уведомление-эскалацию на ответственный за приложение контакт
* __Длина очереди__ Number of message in flight для RabbitMQ
  * Пороговое значение: 90% от, например, 10-кратной пропускной способности (Message delivery rate), чтобы не триггериться на рестарт части консьюмеров
  * Обоснование: если показатель длины очереди превышает выбранный порог, значит имеются проблемы производительности консьюмеров, что отразиться на скорости обработки заказов или даже может привести к их потере
  * Действия при превышении:
    * Сгенерировать алёрт и отправить его по выбранным каналам коммуникации с дежурным инженером (письмо, смс, мессенджер)
    * Завести тикет в трекере задач (например, Jira), чтобы в рабочее время провести анализ производительности.
    * Если утилизация не спадает в течение 10 минут, произвести автоскейлинг, добавив нового консьюмера, чтобы разгрузить очередь
    * Если превышение продолжается более 20 минут, совершить звонок дежурному инженеру и отправить уведомление-эскалацию на ответственный за приложение контакт
* __Число "отброшенных" сообщений__ dead-letter-exchange letters для RabbitMQ
  * Пороговое значение: 2х кратное значение, превышающее обычные значения 
  * Обоснование: может сигнализировать на ошибки в работе консьюмеров MES/CRM или превышение длины очереди из-за слишком высокой скорости публикации продюсерами при некачественном масштабировании
  * Действия при превышении:
    * Сгенерировать алёрт и отправить его по выбранным каналам коммуникации с дежурным инженером (письмо, смс, мессенджер)
    * Завести тикет в трекере задач (например, Jira), чтобы в рабочее время провести анализ производительности.
    * Если превышение 5-кратное и выше, то совершить звонок дежурному инженеру и отправить уведомление-эскалацию на ответственный за приложение контакт
* __Задержки в ответах__ response time (latency) для Shop API, CRM API, MES API и для веб-приложений Shop, MES и CRM
  * Пороговое значение: согласованные с бизнесом SLA для каждого API, например 500 мс на ответ Shop API и 1 с для CRM API
  * Обоснование: превышение сигнализирует о необходимости оптимизации логики сервиса или масштабирования ресурсов, а также ухудшает клиентский опыт
  * Действия при превышении:
    * Сгенерировать алёрт и отправить его по выбранным каналам коммуникации с дежурным инженером (письмо, смс, мессенджер)
    * Завести тикет в трекере задач (например, Jira), чтобы в рабочее время провести анализ производительности.
    * Автоскейлинг здесь не предлагается, т.к. в случае проблем с БД добавление новых нод может окончательно сложить базу
    * Если превышение продолжается более 20 минут, совершить звонок дежурному инженеру и отправить уведомление-эскалацию на ответственный за приложение контакт
* __Длина очереди__ Number of queued requests для Shop API, CRM API, MES API и для веб-приложений Shop, MES и CRM
