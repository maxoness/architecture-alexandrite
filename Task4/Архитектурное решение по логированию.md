# Задание 4. Логирование
## Анализ системы компании и C4-диаграммы в контексте планирования логирования
### Какие логи нужно собирать
Исходя из описания системы можно выделить основные процессы, связанные с деятельностью компании:
* предоставление списка товаров для заказа
* создание заказа (B2C/B2B)
* загрузка 3D моделей для заказа
* расчет стоимости заказа
* подтверждение продавцами заказов с рассчитанной стоимостью 
* предоставление списка новых подтвержденных заказов операторам
* назначение заказа на оператора для выполнения
* изменение статуса заказа в процессе его обработки (от инициации до отправки и подтверждения получения клиентом)
### Из каких систем требуется сбор логов
Соответственно требует сбор логов из систем, управляющих выделенными выше процессами:
* SHOP API:
  * предоставление списка товаров для заказа
  * создание заказа (B2C)
  * загрузка 3D моделей для заказа
  * изменение статуса заказа в процессе его обработки [INITIATED, FILE_UPLOADED, SUBMITTED]
* CRM API:
  * подтверждение заказа продавцом в производство с рассчитанной стоимостью
  * изменение статуса заказа в процессе его обработки [MANUFACTURING_APPROVED, CLOSED]
* MES API:
  * создание заказа (B2B)
  * загрузка 3D моделей для заказа
  * расчет стоимости заказа
  * предоставление списка новых подтвержденных заказов операторам
  * назначение заказа на оператора для выполнения
  * изменение статуса заказа в процессе его обработки [PRICE_CALCULATED, MANUFACTURING_STARTED, MANUFACTURING_COMPLETED, PACKAGING, SHIPPED]
### Список необходимых логов уровня INFO
При нормальной работе системы эти процессы выполняются со стабильной частотой и в пределах SLA
Для контроля потока, детектирования аномалий и SLA нужно единообразно для всех систем реализовать следующие логи уровня INFO:
* создание заказа - __OrderCreated__: {__order_type__: _"b2c"/"b2b"_, __time__, __client_id__, __order_id__, __order_details__ _{[shop_items], comments}_}
* загрузка 3D моделей для заказа - __3dModelUploaded__: {__source__: _"shop"/"mes"_, __time__, __client_id__, __order_id__, __duration__, __object_id__, __object_size__}
* изменение статуса заказа - __OrderStatusChanged__: {__time__, __client_id__, __order_id__, __old_status__, __new_status__, __change_source__: _system_name/"client"/"manual"_, __change_source_manual__: {__id__: _operator_id/seller_id_, __name__: _operator_name/seller_name_}
* подтверждение заказа продавцом в производство - __OrderApproved__: {__time__, __client_id__, __order_id__, __seller_id__, __order_details__ {[shop_items], __price_calculated__, __price_approved__}}
* расчет стоимости заказа - __OrderPriceCalculated__: {__time__, __client_id__, __order_id__, __calculation_duration__, __price_calculated__}
* назначение заказа на оператора - __OperatorAssigned__: {__time__, __client_id__, __order_id__, __operator_assigned__ {__id__: _operator_id_, __name__: _operator_name_}}
* предоставление списка товаров для заказа (в случае, когда duration>=0,95*SLA) - __ShopItemListReturned__: {__time__, __client_id__, __duration__, __shop_item_list_length__}
* предоставление списка новых подтвержденных заказов операторам (в случае, когда duration>=0,95*SLA) - __ApprovedOrderListReturned__: {__time__, __duration__, __approved_order_list_length__}
### Другие уровни логирования и обстоятельства их использования
* ERROR - для логирования ошибок или таймаутов, которые в 1ю очередь произошли при выполнении важных процессов, перечисленных выше. Формат лога такой же + доп. поле про ошибку Error: {__info__, __stack__}
  * OrderCreationError
  * 3dModelUploadingError
  * OrderStatusChangingError
  * OrderApprovingError
  * OrderPriceCalculationError
  * OperatorAssignmentError
  * ShopItemListReturnmentError
  * ApprovedOrderListReturnmentError
* WARN - для предупреждений о потенциальных проблемах, которые не приводят к сбоям, но могут указывать на необходимость внимания. Например:
  * повторные попытки публикации сообщений в RabbitMQ 
  * загрузка/получение подозрительно больших по размеру объектов в S3
  * долгие запросы в БД (e.g. >5 сек.)
* DEBUG - в процессе разработки или исследования проблем в DEV окружении. Например, для сложных взаимодействий между слабо изученными компонентами купленной системы MES API
## Мотивация
Внедрение логирования решает несколько ключевых задач:
* отладка и диагностика: позволяет разработчикам и инженерам при отладке разных компонентов приложения, а также позволяют собирать и анализировать данные о работе системы, значительно сокращая время на обнаружение ошибок.
* аудит и безопасность: логирование действий пользователей и бизнес-процессов позволяет отслеживать аномалии и нетипичное поведение (например, согласование цены заказа ниже рассчитанной MES API), возможные атаки (например, массовые добавления товара в корзину без создания заказа, которые будут грузить БД) и в комплексе обеспечивать безопасность системы.
* улучшение пользовательского опыта: анализ логов помогает выявлять проблемы при взаимодействии с пользователями: высокий отклик, кривой формат данных и т.д., что позволит оптимизировать интерфейсы и процессы
### Технические метрики, на которые может повлиять внедрение решения
* положительно
  * время отклика: логирование помогает выявить узкие места и задержки в обработке запросов
  * частота возникновения сбоев (ROCOF): регулярное чтение и анализ логов позволяют быстро реагировать на аномалии и предотвратить возможные отказы
  * время доступности (UPTIME): логирование позволяет при сбое быстрее найти источник проблемы и устранить его, а значит уменьшить время простоя 
* негативно
  * утилизация CPU: запись подробных журналов требует ресурсы CPU. Важно не переусердствовать с детализацией
  * утилизация памяти: запись больших объемов данных увеличивает нагрузку на оперативку, вымывая в т.ч. кэши
  * утилизация сети: архивация или сбрасывание локальных логов на сетевой ресурс ведет к росту нагрузки на сеть
### Бизнес метрики, на которые может повлиять внедрение решения
* положительно:
  * time-to-market (TTM): логирование, включая Debug, позволяет быстрее делать изменения и исправлять ошибки, найденные при тестировании, а значит поставки в целом осуществляются командой быстрее
  * качество сервиса (SLA): поддерживая высокий уровень доступности сервисов благодаря логированию, мониторингу и быстрому реагированию на инциденты, компания улучшает выполнение соглашений уровня обслуживания
  * уменьшение финансовых потерь: 
    * быстрое устранение неисправностей снижает количество обращений в службу технической поддержки, уменьшая расходы на обслуживание.
    * минимизация рисков репутационных убытков: превентивное выявление и предотвращение сбоев минимизирует риск потери доверия клиентов и негативных отзывов, способствующих снижению продаж
### Системы, для которых нужно настраивать логирование и трейсинг в первую очередь
Для следующий систем нужно настраивать логирование в первую очередь
* MES API: в разделе "Из каких систем требуется сбор логов" видно, что наибольшее количество важных процессов происходит в MES API + это наиболее сложная система + на неё сейчас много жалоб как со стороны операторов, так и со стороны бизнес (долгий обсчет, теряющиеся заказы)
* SHOP API: эта система важна с т.зр. клиентского опыта: с неё начинается привлечение клиентов и именно работая с ней, оформляя заказ, клиент получается первый опыт работы с компаний
Для CRM API достаточно ограничиться трейсингом.
## Предлагаемое решение
### Технологии
Выбираю стек ELK, в том числе потому, что для Tracing-а в качестве хранилища выбрана ElasticSearch
### Компоненты
Развернуть новые:
* Logstash будет собирать, обрабатывать и отправлять логи в Elasticsearch
* Kibana предоставит удобный интерфейс для визуализации и анализа логов
Переиспользовать существующие:
* Elasticsearch для трейстинга также будет использоваться для хранения и поиска логов
Также потребуется:
* доработать кодовую базу систем, перечисленных в разделах выше, для формирования логов в едином формате и покрытия всех важных процессов
* локально около сервисов настроить агенты Filebeat, которые будут отправлять логи в Logstash

### Политика безопасности в отношении логов
* __Идентификация пользователей__
  * Каждый сотрудник, имеющий доступ к системе, должен пройти процедуру идентификации через корпоративную инфраструктуру (например, LDAP или Active Directory).
  * Доступ предоставляется только ограниченному кругу сотрудников, имеющим соответствующую роль («Поддержка», «Администратор» и др.).
  * Использование двухфакторной аутентификации (2FA) путем требования ввода одноразового пароля после успешного входа в систему
* __Мониторинг активности__
  * Журналирование всех действий пользователей в системе с указанием дат, времен и IP адресов
  * Автоматическое оповещение администраторов о подозрительных действиях (необычные входы, попытки изменения конфигурации и другие аномалии)
* __Шифрование и фильтрация данных__
  * Шифрование трафика между компонентами с использованием TLS/SSL сертификатов (filebeat - logstash - elasticsearch - kibana)
  * Шифрование трафика между UI Kibana и пользователем: через HTTPS
  * Запрет на сохранение персональные данных без частичного или полного маскирования на уровне кода, чтобы открытые данные не попадали в сеть
* __Ограничение внешнего доступа__
  * Доступ к инфраструктуре ELK разрешен только внутренним пользователям сети компании
  * Для удаленного доступа обязательно использование VPN с многоуровневой аутентификацией
* __Уязвимость хранимых данных__
  * Ограничить срок хранения логов (например, 60 дней) с последующим удалением
* __Регулярные обновления и патчи__
  * Постоянное обновление программного обеспечения из стека ELK и связанных компонентов инфраструктуры для устранения уязвимостей.
* __Обучение сотрудников__
  * Проведение регулярных тренингов по вопросам информационной безопасности среди сотрудников, имеющих доступ к компонентам ELK
### Политика хранения в отношении логов
* __Индексы__:
  * отдельно по каждой системе: `logs-shopapi-YYYYMMDD`, `logs-mesapi-YYYYMMDD…` и т.д.
  * с сортировкой по убыванию даты-времени
  * структурированы по уровню критичности для фильтрации
- __Горячее хранение__: 30-60 дней в Elasticsearch (в зависимости от наличия свободного места)
- __Архивное хранение__: 365 дней в холодном хранилище S3
## Мероприятия для превращения системы сбора логов в систему анализа логов
### Алёртинг
Для использования всех возможностей логирования нужно переиспользовать алёртинг Grafana, развернутой для трейсинга в связке с ElasticSearch. 
### Аномалии
Алёрты можно слать по следующим аномалиям:
- слишком долгий расчет стоимости заказа: duration > 60 min
- большое количество логов уровня ERROR от одного (e.g. >10 за 1 мин.) или нескольких сервисов (e.g. >50 за 1 мин.)
- аномалии в поведении пользователя (e.g. 10кратный рост заказов за последние 5 минут)
- резкий рост логов уровня INFO от одного из сервисов (e.g. прирост >900% за последние 5 минут). DDOS?
