# Задание 1
## 1.1 Существующие и потенциальные проблемные места
### Существующие проблемы
#### Проблемы бизнеса: 
  * потеря заказов клиентов по неясным причинам, как следствие отток клиентов (м.б. баги в коде или перегруженность MES API или несогласованность статусов заказа в разных частях системы)
  * неполная статусная модель заказа: нет статуса PRICE_CALCULATING "Система начала считать стоимость заказа" для длительной фазы работы над заказом. Из-за этого пользователи не всегда видят актуальное состояние
#### Низкая производительности MES API, особенно после открытия его на других продавцов: 
  * долгая загрузка списка заказов для операторов
  * длительный расчет стоимости заказа
  * дальнейший рост нагрузки приведет к полной остановки системы
#### Низкая надежность:
  * MES API участвует во всех пользовательских сценариях, т.е. является единой точкой отказа => выше вероятность полного отказа всей системы
  * все приложения в единственном экземпляре - отказ одного узла останавливает процесс в контексте приложения
  * все БД в единственном экземпляре - риск потери данных и полной остановки процесса при проблемах
#### Низкая масштабируемость и доступность:
  * все приложения и БД в единственном экземпляре, а значит
    * горизонтальное масштабирование не предусмотрено
    * остановка процессов на время работ по применению изменений в проде
#### Низкое качество тестирования:
  * тестирование проводится вручную => выше вероятность пропустить ошибку из-за неполного покрытия
#### Низкая скорость поставки изменений:
  * релизный цикл 2 недели (еще и постоянно задерживающийся до месяца), из-за чего релизы могут получаться большими и требовать большого тестирования всех частей системы
  * низкая автоматизация процессов CI/CD: деплой поставок в релизную и прод вручную => выше вероятность ошибки и как следствие ниже скорость финальной поставки и ниже качество изменений
#### Низкая наблюдаемость системы:
  * нет мониторинга системных показателей: т.к. открытие MES API на других продавцов значительно ухудшило общую производительность, предварительный анализ системных показателей не проводился  
  * нет средств мониторинга бизнес-метрик: т.к. жалобы на потери заказов поступают от клиентов (банально мониторинг времени выполнения заказа и его этапов), в реальном времени за ситуацией никто не следит
  * нет трейсинга, т.к. в итоге непонятно, где теряются заказы клиентов
### Нестабильная команда:
  * широкий стэк технологий при относительно небольшом размере проекта и команды: Java/C#, Vue/React - команда распыляется
  * риски c# разработки на MES API: только 1 разработчик (тимлид не считает) = bus factor + непредсказуемая поставка изменений
  * риски тестирования: 1 ручной QA без фокуса на автотесты = bus factor + непредсказуемая поставка изменений + отсутствие продвижения в сторону автотестов
  * риски devops: 1 инженер = bus factor + выгорание от стрессово-ответственной работы в одно лицо
  * команда не имеет экспертизы автоматизации => при дальнейшем росте нагрузки начнётся сильное выгорание и потеря сотрудников
## 1.2 Инициативы, необходимые для устранения нежелательных ситуаций в порядке приоритета
  * устранить причины потери заказов:
    * реализовать минимальное логирование, чтобы идентифицировать, где залипают заказы. Полноценное внедрение трейсинга займёт много времени с учетом того, что MES - система не собственной разработки, а размер команды ограничен
    * провести сверку баз данных на предмет остальных потерянных заказов, по которым не было жалоб клиентов
    * настроить мониторинг всех приложений, очередей, БД
    * проанализировать полученные данные мониторинга и зафиксировать приложения с большим количеством ошибок и с высокой утилизацией
    * реализовать паттерн Backpressure применительно к MES API, т.к. его производительность сильно ограничена из-за ресурсоёмких вычислений
    * разобраться с приложениями с большим количеством ошибок и, если причины в логике кода, оперативно исправить
    * поднять дополнительные экземпляры приложений, испытывающих проблемы с производительностью из-за высокой утилизации, + балансировщик
  * поднять реплики БД, чтобы минимизировать риск потери данных
  * найм для расширения команды:
    * C# разработчик, т.к. на ключевой системе MES, испытывающей проблемы и не собственной разработки, только 1 разработчик
    * 1 QA-автоматизатор
    * 1 Java разработчик с ориентацией на DevOps
  * доработать и внедрить статусную модель заказа, для полного отражения всех возможных состояний
    * настроить аналитику заказов по нахождению их в разных статусах
    * настроить алёртинг на Продавцов/Операторов по зависшим заказам
  * ускорить получение списка заказов операторами
    * проверить на оптимальность запросы к MES DB, в частности, что в критичный и открываемый по умолчанию для операторов фильтр считываются именно новые заказы, а не все с последующей фильтрацией в API.
    * при необходимости произвести тюнинг БД: секционирование таблиц заказов по месяцам, реорганизация индексов под топ запросов и т.д.  
    * внедрить кэширование заказов, находящихся в работе
  * поднять дополнительные экземпляры приложений, остановка которых приводит к прекращению продаж и обслуживания клиентов, + балансировщик
  * перенести точку входа для внешних продавцов из MES API в SHOP API:
    * определение SHOP API как единой точки приема заказов даст большее единообразие пользовательских флоу и более выраженный профиль нагрузки по каждому приложению 
    * для MES API останутся только асинхронные интеграции (кроме MES UI, не дающим высокий rps) - унификация профиля рабочей нагрузки в сторону больших объемов ЦПУ или памяти 
  * внедрить трейсинг, чтобы оперативно решать проблемы, подобные непонятным зависаниям заказов
  * перенос приложений в Kubernetes
  * автоматизировать развертывание в релиз и прод окружениях
  * устранить bus-factor в команде: c# и тестирование
  * автоматизиция тестирование:
    * нанять сотрудника с экспертизой в этой области и подключить к автоматизации текущего QA, постепенно увеличивая %% его вовлечения, чтобы в целевой картине уйти от ручного тестирования
    * встроить прогоны автотестов в CI/CD пайплайн
## 1.3 Какой вы видите целевую архитектуру через полгода?
За полгода в первую очередь должна быть снята головная боль бизнеса от потери клиентских заказов и максимально снижены риски повторения ситуации, т.е.:
  * настроен и внедрен в процессы/аналитику мониторинг всех частей системы и соответствующий алёртинг
  * горизонтально масштабированы все критичные приложения и очереди
  * подняты реплики всех БД
  * исправлены баги в коде
Также должны быть завершены начальные этапы долгосрочных работ:
  * перенос приложений в Kubernetes с пакетным менеджером Helm: для CRM API, т.к. там сейчас там нет проблем и накопленного негатива
  * автоматизация CI/CD процессов: для приложений, перенесенных в Kubernetes
## 1.4 Какие три пункта из списка инициатив в ближайшие полгода вы бы выбрали и почему?
  * устранить причины потери заказов <-- это успокоит бизнес и клиентов, позволит планировать следующую веху развития в относительно спокойной обстановке
  * поднять реплики БД, чтобы минимизировать риск потери данных <-- потеря данных компании будет катастрофичной для существования
  * найм требующихся специалистов <-- к моменту начала основных, не "пожарных" активностей через полгода поиск и онбординг как раз завершатся
